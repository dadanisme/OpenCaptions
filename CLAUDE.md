# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**Open Captions** — a native **macOS** app for real-time speech-to-text transcription with speaker diarization, live captions, and AI summaries. SwiftUI + SwiftData, macOS **14.4+**. It is **not** Mac Catalyst and shares no code with any other platform: it was extracted from a larger multi-platform codebase into this standalone project, and now has **no backend at all** — no accounts, no cloud database. Uses Soniox (cloud STT), **OpenRouter** (AI summaries, called straight from the app — there is no summarization server), and FluidAudio (on-device inference), each gated by a single app-wide API key rather than any account. All transcription is **free and unmetered** — there is no billing, metering, or paywall.

Core flow: capture mic **and/or** other apps' system audio → stream to a real-time STT engine → render a live diarized transcript → flush lines to local SwiftData in batches *during* the session (past `TranscriptionConstants.flushThreshold` = 70, not only at Stop) → optional AI summary, which also auto-names the diarized speakers. A fully on-device **Offline Mode** (Nemotron via FluidAudio) transcribes with no network *once its models are on disk* — enabling it first requires a one-time download of both the Nemotron and Parakeet CoreML bundles (`FluidAudioModelLoader`; the Settings row stays a Download control until both report `.ready`). As a consequence of running on-device it gets no diarization, no term biasing, and no summary.

## Naming — fully renamed to Open Captions

The app was extracted from a larger multi-platform codebase and has since been **fully renamed and separated** into a standalone **Open Captions** project. The rename is complete in symbols, UI copy, and identifiers. The only surviving mentions of the old name in **Swift source** are two **provenance comments** — `SummaryService+OpenRouter.swift:16` and `SummaryService+Prompt.swift:6` both cite `ogmo-cf/summarizeTranscript.ts` as the source the prompt was ported from (`docs/2026-07-24-macos-native-gemini-summary.md` names it three more times, as history). Those are deliberate provenance, not branding; don't "fix" them into meaninglessness.

- **Xcode + files:** project/scheme/target/product (`OpenCaptions.app`), display name, Info.plist strings, and all file/folder/asset names (`OpenCaptions/`, `OpenCaptionsApp.swift`, `OpenCaptionsAEC.{h,mm}`, `opencaptions-logo`, …).
- **Bundle id:** `com.muhammadramdan.OpenCaptions` — set in `project.pbxproj`, the `OpenCaptions.entitlements` keychain-access group, and 3 audio `Logger(subsystem:)` labels. Core Audio self-process identification reads it dynamically via `Bundle.main.bundleIdentifier`, so it needs no per-file literal.
- **Code symbols:** `OpenCaptionsApp` (the `@main` struct in `OpenCaptionsApp.swift`), `OpenCaptionsCommands`, and `OpenCaptionsAEC` (the Obj-C class in `OpenCaptionsAEC.{h,mm}`, exposed through `OpenCaptions-Bridging-Header.h`). These three type names now match their file names — that is a statement about the rename, not a repo-wide convention (`Utility/Sonioxsecrets.swift` declares `enum SonioxSecrets`, among a few other file/type mismatches).
- **UI copy:** every user-facing string reads "Open Captions".
- **Misc identifiers:** Carbon four-char hotkey code `'OpCp'` (`0x4F704370`); window autosave name `"OpenCaptionsCaptionsOverlay"`; UserDefaults keys are *mostly* `opencaptions.*` — the one exception is `hasCompletedOnboarding` (the sole launch-gate flag, read by `@AppStorage` in `OpenCaptionsApp`); the SpeexDSP include guard `OPENCAPTIONS_SPEEXDSP_CONFIG_H`.
- **Backend / services:** there is **no backend** — the app depends only on Soniox and OpenRouter, each a plain per-deployment API key supplied via the git-ignored `Config.xcconfig` **or** entered at runtime in Settings → API Keys (Keychain-backed, `APIKeyStore` — see **Credentials** below); **no credentials are hardcoded in committed source.** Non-secret infra *is* literal, though, and a fork must change it by hand: the bundle id and the Soniox / OpenRouter endpoints. The support email is config-driven (`SUPPORT_EMAIL`) and stays build-time only — it isn't a secret. The former summarization endpoint (`SUMMARIZE_URL`) is gone for good: summaries call OpenRouter directly from the app (see **AI summaries** below). A developer moving to their own deployment only needs their own bundle id and the git-ignored `Config.xcconfig` filled in — there's no account system or Cloud project to re-register.

## Build & Run

Open `OpenCaptions.xcodeproj` in Xcode (macOS 14.4+ SDK), select the **`OpenCaptions`** scheme, build & run. There are **no unit tests**. Build in Xcode, or via the Xcode MCP's `BuildProject` when connected — never shell out to the `xcodebuild` CLI directly (see **Xcode MCP (preferred)** below).

The signing team that actually applies is `C4SQMCY5WT`, set on the **target** in both configurations. Note there is a *second*, stale team — `YN8NVQ69WY` — still committed at the **project** level, alongside iOS leftovers from the extraction (`SDKROOT = iphoneos`, `IPHONEOS_DEPLOYMENT_TARGET = 17.0`). The target's macOS settings override all of it, so the build is correct, but a developer told to change "the" team will find two. A different developer must set their own team and, if desired, their own bundle id — there's no backend to re-register against.

**Filesystem-synchronized groups** (Xcode 16 `PBXFileSystemSynchronizedRootGroup`): new files added anywhere under `OpenCaptions/` are picked up **automatically** — never hand-edit `project.pbxproj` to add a file. No source-file references live in the pbxproj — only build settings (the Info.plist / entitlements / bridging-header / header-search paths, plus the bundle id, signing teams, deployment target, and four `INFOPLIST_KEY_*` values that include user-facing copy).

### Credentials (git-ignored)

- **`Config.xcconfig`** (repo root) — injected into the build; **three** keys: `SONIOX_API_KEY`, `OPENROUTER_API_KEY` (bring-your-own key for AI summaries — https://openrouter.ai/keys), `SUPPORT_EMAIL`. Copy `Config.xcconfig.example` to start. All three are **top-level keys** in `OpenCaptions-Info.plist`, `$(...)`-substituted and read via `Bundle.main.infoDictionary`. Adding a *readable* key here without adding it there leaves it unreadable at runtime. Beware that the example's `YOUR_OPENROUTER_API_KEY` placeholder is non-empty, so it passes the emptiness guard and fails later — as an HTTP **401** now, which at least maps cleanly onto `.unauthorized` (the old Gemini key surfaced as a 400 needing a message-sniffing hack).
- **Runtime override (Settings → API Keys)** — `SONIOX_API_KEY` and `OPENROUTER_API_KEY` can *also* be entered/edited at runtime, so a prebuilt `.app` the user didn't compile themselves can still be handed real credentials. Stored in the Keychain via `Utility/APIKeyStore.swift` (a private, non-shared generic-password item per key — needs the `keychain-access-groups` entitlement, re-added for this after being dropped by `10f221e`/#36), never UserDefaults, since these are secrets rather than preferences. `SonioxSecrets.sonioxAPIKey` and `SummaryService+OpenRouter.apiKey()` each prefer the runtime value and fall back to the `Config.xcconfig` one above; a missing key on both paths is a normal, recoverable runtime state, not a launch-time crash. `SUPPORT_EMAIL` has no runtime counterpart — it isn't a secret. See `docs/2026-08-10-macos-runtime-api-keys.md`.

## Architecture (MVVM + Services)

Source is under `OpenCaptions/` (`Model/`, `Services/`, `ViewModel/`, `Views/`, `Utility/`, `AEC/`, `ThirdParty/`). The pieces that need several files to understand:

- **Transcription state machine** — `MacTranscriptionViewModel` (+ **7** `+` extension files: `+AppMonitor`, `+AudioRecording`, `+AudioSource`, `+Engine`, `+Lifecycle`, `+Lines`, `+Persistence`) drives a session. `+Lines` and `+Persistence` replaced the old `+Accumulator` in `d6855d2`: there is **no token buffer any more** — each finalized token is committed straight into `TranscriberModel` as it arrives, and `+Persistence` flushes to SwiftData mid-session. A session **outlives its window**, so session-scoped state (the keepalive) lives on the view model / stores, never on a view. `failSession(message:)` is the single abort path (connection loss, mic failure, audio-route change): it stops capture and closes the socket **while keeping the transcript**, so Stop & Save still persists what was captured.

- **Cloud STT (Soniox)** — `Services/Transcription/OnlineTranscriberService` (+`+ConnectionHealth`, `+Messages`) is a `URLSessionWebSocketTask` client to `wss://stt-rt.soniox.com/transcribe-websocket`. The JSON config is sent as the **first frame** right after `resume()` (sends queue FIFO until open — no startup sleep), and it carries `SonioxConfig.context`, the custom-vocabulary payload. That frame is **never resent**, so vocabulary is read exactly once at session start and edits mid-session do not apply. During a soft pause a 15 s `RunLoop` keepalive holds the idle socket under Soniox's ~20 s timeout; because macOS **App Nap** throttles that timer when backgrounded, a `ProcessInfo.beginActivity(.userInitiated)` assertion is held for the whole running-or-paused session (also disables idle sleep).

- **On-device STT (Offline Mode)** — Nemotron / Parakeet via **FluidAudio** (`Services/Transcription/*` + `Utility/OnDeviceModels/FluidAudio*`). English-only, single-stream, unmetered. Post-session re-transcription lives in `Services/Retranscription/`. Three capabilities are cloud-only and simply absent here, which is a frequent source of "why is this empty" questions: **no diarization** (every on-device engine sets `supportsDiarization: false` — `NemotronTranscriberService`, `ParakeetTranscriberService`, and `ParakeetPostSessionEngine` — so lines carry no speaker id and thus no speaker name), **no term biasing** (the Nemotron engine config takes no context argument), and **no AI summary**. That last one is gated in four places off the *global* `offlineModeKey` preference, not off how the session was captured: `MacSessionDetailView.autoSummarizeIfNeeded`, the Re-summarize menu item's `.disabled(isOffline …)`, the Summary tab's offline empty state, and `PostSessionRetranscriber`. So an offline-captured session *can* be summarized later by turning the toggle off.

- **Custom vocabulary (term biasing)** — `Utility/Vocabulary/VocabularyStore` (+`+Persistence`, `+SonioxContext`) is an `@Observable @MainActor` singleton holding the user's terms plus an optional freeform background note, edited in the **Vocabulary** sidebar section (`Views/Vocabulary/`, a `NavSection` destination rather than a Settings pane because it's a variable-length list editor) and persisted to two `opencaptions.vocabulary.*` UserDefaults keys. It loads eagerly in `init`, because a session can start from the menu bar with the main window never opened. It is **device-local** — there's no backend to sync it to. `sonioxContext(userName:)` is the **single** place the wire payload is assembled — the Settings → General "Your Name" preference (`LiveSessionStore.yourName`), then the non-editable built-ins, then the user's terms in editor order, then the background note into whatever character budget is left, deduped case-insensitively. Only the **Soniox** paths consume it — the live socket (`+Engine`), post-session re-transcription, and audio file import (the last two share `PostSessionRetranscriptionFactory`); see Offline Mode above.

- **AI summaries (OpenRouter, no backend)** — `Services/SummaryService` (+`+OpenRouter` transport, `+OpenRouterResponse` decoding, `+Prompt` system instruction, `+Schema` JSON Schema) POSTs the flat transcript to `https://openrouter.ai/api/v1/chat/completions` with the bring-your-own `OPENROUTER_API_KEY` as a **`Authorization: Bearer` header** (never in the URL, so the key stays out of URL logs). The model is **pinned** to `google/gemini-3.1-flash-lite` with no user-facing picker. This replaced a direct Gemini `generateContent` call on 2026-08-04 (see `docs/2026-08-04-macos-openrouter-summaries.md`) — the whole point was overload tolerance, so **two mechanisms handle it and both matter**: `provider: {allow_fallbacks: true, require_parameters: true}` lets OpenRouter route around a saturated upstream (the pinned model is served by both Google Vertex and Google AI Studio), and the transport retries `408/429/502/503` twice with a 1 s → 4 s backoff, honoring a clamped `Retry-After`. Only when all three attempts come back busy does it throw `.overloaded`, which has its own user-facing copy rather than a raw `Server error:`. `SummaryAPIResponse` is unchanged by either migration — only the transport ever moved; the optional `speakers` array that drives auto-naming rides along in it. Three non-obvious traps: the `responseSchema` type names must now be **lowercase** JSON Schema spellings (`object`/`string`/`array`) — the uppercase `OBJECT`/`STRING`/`ARRAY` were Gemini-REST-only and will not work here; the envelope is decoded with `.convertFromSnakeCase` but the summary JSON *inside* `choices[0].message.content` must use a **plain** decoder (its keys are camelCase — `shortDescription`, `keyPoints`); and a **200 can still carry a failure** in `error` or `choices[0].finish_reason`, so success is not the status code alone.

- **Speaker naming** — diarized lines land as generic `Speaker N` labels and the summary pass names them. The summary response schema carries an optional `speakers` array (deliberately **not** in `required`), and the prompt admits only two kinds of evidence — self-introduction or direct address — never a role, topic, or third party. `Services/Speakers/` decides alone: `SpeakerNameResolver` owns **both** thresholds (a single candidate above `0.85` wins outright; otherwise every candidate above `0.35` is slash-joined, `"Simon/Sam"`; nothing above `0.35` keeps the generic label) — the model is never told those numbers. `SpeakerRenamer.apply(_:to:context:)` is the **single write path for a saved session** (fan the name across every line of that id → `save()` → re-export markdown) and never throws, because one of its callers is a throwaway `SummaryViewModel` whose error nobody reads. Manual renames (the batch Edit Speakers sheet and the per-bubble right-click sheet) stay **ungated** by the auto-naming preference, since an explicit rename is always authoritative. During a **live** session the same sheet instead calls `MacTranscriptionViewModel.rename(speaker:to:)`, which updates `speakerMapping` + `finalLines` and **never touches SwiftData** — so a rename written through `SpeakerRenamer` does not refresh a still-alive live view, and vice versa. `ConversationFormatter.buildTranscript` (the model-facing transcript, exactly one caller — user-facing exports use `MarkdownFormatter`) must keep the numeric id in every label, or a re-run has nothing for `speakerId` to refer to.

- **Audio capture** — `Services/Audio/`. Mic via an `AVAudioEngine` input tap → 16 kHz mono (no `AVAudioSession` — macOS has none). **System audio uses Core Audio process taps** (`SystemAudioTapCaptureService` + `CoreAudioTapUtils`), **not** ScreenCaptureKit. The mixed mic+system source (`MixedAudioCaptureService`) uses a **plain** mic engine (no VPIO — the mic tap must stay passive/read-only) and cancels speaker bleed **in software** via `OpenCaptionsAEC` — an Obj-C++ bridge (`AEC/OpenCaptionsAEC.{h,mm}`, exposed through `OpenCaptions-Bridging-Header.h`) over a **vendored six-file SpeexDSP subset** (`ThirdParty/SpeexDSP/`, pure C, BSD-3, compiled into the target — not SPM).

- **Metering** — none. All transcription (cloud Soniox and Offline Mode) is free and unmetered: there is no minute balance, deduction, gate, or paywall. RevenueCat and the whole billing subsystem were removed in `73cf54d` — **7** Swift files, including the entire `Utility/Billing/` directory, `MacPaywallView`, `MacUsageSettingsView`, and the `MacTranscriptionViewModel+Billing` clock. There is no RevenueCat SPM dependency and no `StoreKit` import anywhere; every session start, re-transcription, and file import is always-allowed. One artifact outlived the purge: `OpenCaptions/OpenCaptions.storekit` still declares the three old consumables (`extra_3_hours`/`extra_10_hours`/`extra_25_hours`). Nothing references it — not `project.pbxproj`, not any scheme — so it is dead weight, not a live product list.

- **Remote configuration** — none. Every feature is compiled in and **always enabled**; there is no feature-flag reader, no remote config document, and no remote kill switch (there's no backend to host one). `FeatureFlag` / `FeatureFlagService` and the three self-re-arming `withObservationTracking` flag observers were removed (2026-07-27); session playback, post-session re-transcription, mixed-source AEC, and file import are all unconditional. Local per-device Settings toggles (`LiveSessionStore.sessionAudioKey`, `retranscriptionAutoKey`, and `speakerNamingAutoKey` — `"opencaptions.speakerNaming.auto"`, default `true`, Settings → Speaker Names) are user preferences, not flags — do not confuse the two. `speakerNamingAutoKey` is the one most likely to be mistaken for a flag, since it gates an AI behavior.

- **No accounts** — there is no sign-in of any kind, and no `Utility/Auth/` directory. `OpenCaptionsApp` gates on a single flag, `hasCompletedOnboarding`, → `ContentView`, else `MacOnboardingView`; there is no signed-in/guest distinction to check alongside it. Every session, whoever opens the app, reads and writes the same single local library — there is no uid scoping anywhere in the SwiftData model (`TranscriptionSession`/`Workspace` have no `userId` field) and no equivalent of the old `SessionOwnerBackfill`. Cloud Soniox transcription (diarization, custom vocabulary, AI summaries) is available unconditionally to everyone; the old "guest locked to Offline Mode" restriction doesn't exist because there's no guest concept to lock. The onboarding Mode step still offers a Cloud-vs-Offline choice, but it's a pure accuracy/privacy tradeoff — signing in was never part of it. The one thing that used to ride on the signed-in identity — the display name fed into Soniox's context, the vocabulary screen's always-included term, and the `@Name` mention-highlight/notify feature — now comes from a plain local preference, `LiveSessionStore.yourName` (Settings → General → "Your Name"). See `docs/2026-08-10-remove-accounts-and-firestore.md`.

- **Markdown export** — `Services/Export/` mirrors **every** session to disk continuously, always on, no toggle: `<root>/<yyyy-MM-dd>-<slug>/{transcript.md, summary.md, audio.m4a}`. `SessionExportCoordinator` is the façade the seven mutation sites call (session save, import, summary, re-transcription, speaker rename, action-item toggle, launch backfill) plus three delete sites; `SessionMarkdownWriter` is an `actor` doing all the I/O. Disk is a **projection** of SwiftData — files are rewritten whole, never appended, and a failed write is logged, never fatal. Three things to know: `TranscriptionSession.exportFolderName` persists only the *relative* folder name (the `audioFileName` precedent) — it's what lets a retitle rename instead of orphan; a session with no summary exports **no** `summary.md`, which is how re-transcription's cleared summary leaves disk; and the destination is a **security-scoped bookmark**, not a path, needing `com.apple.security.files.bookmarks.app-scope` — before the user picks one (Settings → General → Markdown Export → Browse…) the root is the app's own container `Documents/Open Captions`. It is the **only** way to get a session out of the app — there is no cloud sync or web sharing. See `docs/2026-07-31-macos-markdown-export.md`.

- **App shell & windowing** — `OpenCaptionsApp` declares **two** scenes: `Window(id: MainWindowID.main)` (a `Window`, not a `WindowGroup`, so the menu-bar item can reopen it via `openWindow(id:)`) and `MenuBarExtra`. There is no `Settings { }` scene — Settings is a `NavSection` destination like any other, rendered in the main window's detail column (see below), not a separate window. `OpenCaptionsCommands` holds the menu commands reading `@FocusedValue`; `LiveSessionStore` / `MenuBarState` are the app-wide observable stores. The sidebar's destinations are `NavSection`: `transcriptions`, `actionItems`, `keyPoints`, `vocabulary`, `workspaces`, `settings`. `.settings` is excluded from the sidebar's scrollable `List` and rendered instead by `Views/Shell/SidebarSettingsFooter.swift`, a row pinned below it via `.safeAreaInset` (mirroring the old separately-styled Settings entry): "Open Captions, v⟨CFBundleShortVersionString⟩" leading, and a trailing icon-only button (filled + tinted while `.settings` is the current section) that sets `section = .settings` directly rather than opening a window — there is no "Settings" text label on the row itself. Cmd+, is no longer free from a `Settings { }` scene, so `OpenCaptionsCommands` fills the `.appSettings` `CommandGroup` placement itself, reading an `openSettings` `@FocusedValue` (`Utility/HotKeys/MacFocusedValues.swift`) that `ContentView` publishes unconditionally (not tied to any one screen, since Settings access shouldn't depend on which section is frontmost). `openSettings` is nil whenever the main window is closed — a state the app explicitly supports via `MenuBarExtra` — so that case falls back to `LiveSessionStore.pendingSection` + `openMainWindow?()` (the same reopen mechanism the global-hotkey Start fallback uses), which `ContentView.onAppear` consumes once the window (and it) reappear. `MacSettingsView` (`Views/Settings/`) has four panes — General, Shortcuts, Support, API Keys (General's sections: Your Name, Appearance, Captions, Sessions (Session Audio, Re-transcription, Speaker Names, Markdown Export rows), Offline Mode; API Keys holds the runtime Soniox/OpenRouter overrides, see **Credentials** above) — no longer boxed into a fixed 480×460 frame, and switched via a native segmented `Picker` centered in the toolbar (`.principal` placement) rather than a `TabView`'s own tab bar, matching `MacSessionDetailView`'s Summary/Transcript switcher. Every row's explanatory copy that used to sit inline as a `.caption`/`.secondary` paragraph now lives behind a `SettingsInfoTip` "i"-icon popover (`Views/Settings/SettingsInfoTip.swift`) next to that row's label instead, so the wider column reads as controls first. See docs/2026-08-10-macos-settings-navsection.md. Also: global hotkeys (`Utility/HotKeys/`, Carbon), a captions overlay + HUD (`Utility/Overlays/`), name-mention highlight/notify (`Utility/NameMention/`), and file import (`Services/Import/`).

- **Appearance** — **two independent font-size sliders**: the transcript/captions size (`Font.transcript`, applied in `MacLiveTranscriptionView` / `CaptionsOverlayView`) and the app-wide UI size (`Utility/Appearance/AppTextSize.swift`, applied via `.appScaledFont(_:)` + a root `.appTextScaling()`). They write different keys and never affect each other.

## Coding Standards

The code was written under these conventions — keep matching them:

- **~250-line limit per file** — split responsibilities across `Type+Feature.swift` extension files (see the many `MacTranscriptionViewModel+*` / `MixedAudioCaptureService+*` files) rather than growing one file. It is a target, not an invariant: 155 of 163 non-`ThirdParty` Swift files comply, and 8 exceed it (worst: `LiveSessionStore.swift` 422, `MacTranscriptionViewModel.swift` 393). Treat those as debt to split, not licence to add a ninth.
- **macOS ignores Dynamic Type** — never hardcode point sizes for general UI. Use **`.appScaledFont(_:)`** (not `.font(_:)`) on sidebar/list/detail/settings/sheets so text honors the app-wide font setting; unstyled text inherits the scaled default. The live transcript + captions overlay are the exceptions (they use `Font.transcript(...)`, the separate transcript-size mechanism).
- `camelCase` / `PascalCase` / `UPPER_CASE`; boolean `is`/`has`/`should`/`can`/`will`; `async/await` over completion handlers with `[weak self]`; `// MARK:` sections where a file has distinct regions (about half the files do); one clear responsibility per file.
- **No force-tries and no force-casts** — `try!` and `as!` are at literal zero in the target; keep them there. Force-*unwraps* are near-zero: two `URL(string:)!` on hardcoded literals (the Soniox WebSocket and REST base URLs). One `fatalError` exists, on unrecoverable launch config — `ModelContainer` init. Don't add more of any of these; a missing/invalid API key is a normal, recoverable runtime state (Settings → API Keys) rather than a launch-time crash — `SonioxSecrets.sonioxAPIKey` used to `fatalError` on a missing key and no longer does, see **Credentials** above.

## Documentation

`docs/` is the knowledge base — dated design/decision notes (`{YYYY-MM-DD}-{topic}.md`) covering the audio pipeline, AEC, system-audio capture, onboarding, offline mode, the backend-less AI summary, custom vocabulary, speaker auto-naming, markdown export, and more. **`docs/README.md` is the index** — every note with a one-line description and a Current/Historical status, kept current at the source: a historical note also carries its own "superseded by X" banner, so opening one directly still gives the signal without a detour through this file.
